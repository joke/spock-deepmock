`spock-deepmock` adds deep mocking capabilities to the http://spockframework.org/[Spock Framework].

In contrast to builtin https://spockframework.org/spock/docs/2.4/interaction_based_testing.html[mocks]
a deep mock will return another deep mock object automatically. This way there
is no need to define chains of nested mocks.

* Adds `DeepMock()` and `GroovyDeepMock()` for deep mocking
* Build deep mocking chains for nested objects
* Uses same syntax as the builtins `Mock()` and `GroovyMock()`
* Supports interaction verification
* Works with Spock Framework 2.4 (on Groovy 4.0)

== Requirements

* Spock Framework 2.4 or later
* Java 8 or later
* Tested with Groovy 4.0

== Usage

`DeepMock()` and `GroovyDeepMock()` accept all argument forms and options of `Mock()` and `GroovyMock()`, except `defaultResponse`, which is rejected.

.Define deep mocks
[source,groovy]
----
def mock = DeepMock(Nested)
Nested mock = DeepMock()

def mock = DeepMock(name: 'customName')
Nested mock = DeepMock(name: 'customName')

Nested mock = DeepMock(mockMaker: MockMakers.byteBuddy)
Nested mock = DeepMock(verified: false, Nested)
Nested mock = DeepMock { name >> 'Fred' }
Nested mock = DeepMock { it.child.name >> 'Hello' }
----

A chain in an interaction closure must start with `it.`, as for all Spock mocks.
Spock adds the mock only in front of a single name such as `name >> 'Fred'`.
In `child.name >> 'Hello'`, Groovy looks for `child` in the specification and fails with a `MissingPropertyException`.

Options and types can come from variables.

.Options and types from variables
[source,groovy]
----
def options = [name: 'customName']
Class type = Nested

def mock = DeepMock(type)
def mock = DeepMock(options, type)
----

.CallerTest.groovy
[source,groovy]
----
def 'calling nested mock'() {
    setup:
    Nested mock = DeepMock()
    def caller = new Caller(mock)

    when:
    // calls mock.getChild().getChild().getName()
    def res = caller.call()

    then:
    1 * mock.child.child.name >> 'Hello'

    expect:
    res == 'Hello'
}
----

Further examples in link:examples/src/test/groovy/io/github/joke/test[].

== How deep mocks answer

`DeepMock()` creates a Java mock and `GroovyDeepMock()` creates a Groovy mock.

An unstubbed call on a deep mock returns a nested mock of the return type of the call.

* Each call has its own nested mock. `mock.child` and `mock.getChild()` return the same nested mock.
* The same call with equal arguments returns the same nested mock. `mock.child('first')` returns the same nested mock each time, while `mock.child('second')` returns another one.
* A nested mock lives as long as the specification instance that created it.
* A return type that the mock makers cannot mock gets the answer of a `Mock()`: `null` for `void` and reference types, and the default value for primitive types. This applies to `void`, primitive types, arrays, `String`, `Integer` and other types that cannot be mocked.
* Nested mocks have path names that show the call that produced them, for example `nested.getChild().child('first')`. Failure messages show these names.

Stub a call when a test needs a value from it, for example `mock.name >> 'Hello'`.

== Options

A nested mock inherits these options of the deep mock that created it:

* `mockMaker`, when the parent sets one
* `verified`
* `useObjenesis`

A nested mock does not inherit these options. They apply to the parent type only:

* `name`: a nested mock has a path name
* `additionalInterfaces`
* `global`
* `constructorArgs`

The option `defaultResponse` is rejected.

== Chains and interactions

An interaction on a chain, such as `1 * nested.child.child.name >> 'Hello'`, also declares the steps of the chain as `_ * nested.getChild()` and `_ * nested.getChild().getChild()`. A step is matched like any other interaction, and it never counts invocations. Code under test can therefore make the calls of a declared chain without matching a catch-all interaction.

.Chain with a catch-all
[source,groovy]
----
def 'calling nested mock'() {
    setup:
    Nested mock = DeepMock()
    def caller = new Caller(mock)

    when:
    def res = caller.call()

    then:
    1 * mock.child.child.name >> 'Hello'
    0 * _

    expect:
    res == 'Hello'
}
----

The following rules apply:

* `0 * _` works in any position, before or after a chain.
* An interaction that verifies a step of a chain must come before the chain. A step verified after the chain fails with a `TooFewInvocationsError`, as it does for a plain Spock `_ *` interaction declared first.
* A specification must not stub a step to another object and also use a chain through that step. The stub is bypassed while the chain is evaluated.
* A chain declared only in `given:` does not pass a `0 * _` in `then:`, as for all Spock interactions.

== Migrating from 4.x

* `GroovyDeepMock()` creates a Groovy mock. Before, every `GroovyDeepMock()` overload created a Java mock.
* Each call has its own nested mock. Before, overloads with equal arguments, such as `lookup(String)` and `lookup(Object)`, could return the same nested mock.
* Nested mocks live as long as the specification instance that created them. Before, one static cache kept them for the whole JVM.
* A return type that the mock makers cannot mock gets the answer of a `Mock()`. Before, the call threw `CannotCreateMockException`.
* Nested mocks have path names. Before, every nested mock had the name of the top-level mock.
* Evaluating a chain in an interaction declaration no longer counts invocations. Specifications that compensated for this count must use the real count.
* Spock 2.4 is necessary.
